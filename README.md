# My Blog

A deliberately small, read-only blog served as a **single ASP.NET Core MVC
application**:

- **Backend** — ASP.NET Core MVC (`Blog.Api`), EF Core, **Azure SQL Database**
  storage. Exposes a JSON API (`/api/posts`) and an MVC view that hosts the
  built front-end.
- **Frontend** — React + TypeScript (Vite), Markdown rendering. `vite build`
  emits the SPA into `backend/wwwroot`; a Razor view references the hashed
  assets via Vite's manifest.
- Anyone can read published posts. There is no sign-in or authoring UI.
  A background service mirrors published Markdown files from
  `https://github.com/gaufung/Blog/tree/master/blogs` into the database.

```
blog/
  backend/    ASP.NET Core MVC app (Blog.Api) — serves the API and the SPA
    Views/    Razor shell that renders the built front-end
    wwwroot/  Front-end build output (generated by `vite build`)
  frontend/   Vite React TypeScript app (source)
```

The front-end and API run on the **same origin** — the backend serves the
compiled React app, so no CORS configuration is required.

## 1. Azure setup (one time)

### Azure SQL Database
1. Create an Azure SQL Server + Database (e.g. `BlogDb`).
2. Put the connection string in `backend/appsettings.json` →
   `ConnectionStrings:DefaultConnection`. Two common options:
   - **Entra auth** (recommended): keep `Authentication=Active Directory Default`
     and sign in locally with `az login`.
   - **SQL auth**: `Server=...;Database=BlogDb;User ID=...;******;Encrypt=True;`

## 2. Build & run (single application)

`dotnet build` automatically builds the front-end (it runs `npm install` when
needed, then `npm run build` into `backend/wwwroot`). So a single command
builds and runs everything:

```bash
cd backend
dotnet run   # builds the SPA, applies EF migrations, then serves the app
```

Then open the URL printed by `dotnet run` (e.g. `http://localhost:5133`). The
same origin serves both the site and the `/api/posts` endpoints.

The front-end build is incremental — it only re-runs when files under
`frontend/` change. To skip it entirely (e.g. in CI where the SPA is built
separately), pass `-p:SkipFrontendBuild=true` to `dotnet build`/`dotnet publish`.

## 3. Front-end development (hot reload)

For fast iteration on the React app, run the Vite dev server alongside the
backend. `/api` requests are proxied to the backend (see
`frontend/vite.config.ts`), so no extra configuration is needed:

```bash
# Terminal 1 — backend API
cd backend
dotnet run

# Terminal 2 — Vite dev server (http://localhost:5173)
cd frontend
npm install
npm run dev
```

To point the front-end at a differently-hosted API, set `VITE_API_BASE_URL`
in `frontend/.env` (see `.env.example`). Leave it empty for the same-origin
setup above.

## Notes
- Database schema is created/updated automatically via EF Core migrations
  (`backend/Migrations`) on app startup.
- GitHub content is synchronized on startup and every six hours. Configure the
  source and interval with the `GitHubBlogSync` section in
  `backend/appsettings.json`. Set `GitHubBlogSync__Token` through environment
  configuration if authenticated GitHub API requests are needed.
- The latest 50 published posts are available as an RSS 2.0 feed at `/rss.xml`.
- Markdown filenames must use the `<number>-<title>.md` format. The numeric
  prefix controls newest-first ordering. Front matter supplies `name`, `tags`,
  and `status`; only `status: publish` files are stored, and the front matter is
  excluded from the stored content. The synchronizer also accepts the existing
  repository's `tages` spelling.
- The GitHub snapshot is authoritative: database posts whose titles are absent
  from the published source files are deleted, and newly discovered tags are
  created automatically.
- Only posts with `Published = true` are returned by the API.
- Markdown is stored as-is and rendered with `@uiw/react-md-editor`.
- `backend/wwwroot` is generated by `vite build` and is git-ignored — rebuild
  the front-end whenever it changes.
